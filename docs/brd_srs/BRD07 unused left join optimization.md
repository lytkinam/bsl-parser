# BRD07: Оптимизация FFL — исключение неиспользуемых LEFT JOIN

## 1. Цель

На основании урезанной структуры `full_field_lineage` (FFL) исключить LEFT JOIN'ы, которые не влияют на результат конкретного поля запроса. Это уменьшает объём восстановленного SQL, повышает его читаемость и позволяет сфокусироваться только на значимых источниках данных.

## 2. Проблема

В пакетных SQL-запросах 1С (SDBL) часто встречаются запросы с большим количеством LEFT JOIN'ов. Например, в отчёте 0420258 (форма НПО) узел `ВТ_РезультатПредв_UNION_0` содержит 21 LEFT JOIN из 26 соединений. При построении FFL для конкретного поля (например, `Взносы26`) большинство этих LEFT JOIN'ов не участвуют ни в SELECT, ни в WHERE, ни в GROUP BY, ни в HAVING данного поля — они присутствуют в FFL только потому, что были в исходном запросе.

### 2.1 Пример из example_258

Узел 296 (`ВТ_РезультатПредв_UNION_0`) для поля `Взносы26`:
- SELECT: `ЕСТЬNULL(ВТ_Суммы.Взносы, 0)` — использует только `ВТ_Суммы`
- WHERE: `ВТ_ПенсионныеСчета_Свойства.ТипПенсионногоСчета = 3` — использует основную таблицу
- INNER JOIN'ы (5 шт.) — фильтруют строки, оставляем
- LEFT JOIN `ВТ_Суммы` — используется в SELECT, оставляем
- LEFT JOIN'ы `ВТ_СхемыПенсионныхСчетов`, `ВТ_ФизическиеЛица`, `ВТ_СостоянияПенсионныхСчетов`, `ВТ_МГД`, `ВТ_ПериодичностьВыплат` и 16 других — **не используются ни в SELECT, ни в WHERE, ни в GROUP BY, ни в HAVING, ни в условиях последующих используемых JOIN'ов**

## 3. Требования

### 3.1 Критерий неиспользуемого LEFT JOIN

LEFT JOIN считается **неиспользуемым** (и подлежит исключению из FFL) если одновременно выполняются условия:

1. Тип соединения — `left` (не `inner`)
2. **Ни alias, ни table** этого JOIN'а не встречаются в:
   - `select[].child_fields[].nodeName` / `source`
   - `where_fields[].child_fields[].nodeName` / `source`
   - `group_by_fields[].child_fields[].nodeName` / `source`
   - `having_fields[].child_fields[].nodeName` / `source`
3. **Ни alias, ни table** этого JOIN'а не встречаются в `condition_fields` **последующих** JOIN'ов (с большим индексом в массиве), которые **сами являются используемыми**

### 3.2 INNER JOIN'ы не удаляются

INNER JOIN'ы никогда не исключаются, даже если их поля не используются напрямую. INNER JOIN фильтрует строки (изменяет количество возвращаемых записей), поэтому его удаление может изменить результат запроса.

### 3.3 Правое сканирование (right-to-left)

Анализ JOIN'ов выполняется **справа налево** (от последнего к первому). Если JOIN N используется, и его условие ссылается на таблицу из JOIN N-1, то JOIN N-1 становится "используемым" через condition_fields, даже если его собственные поля нигде не фигурируют.

### 3.4 Вложенные JOIN'ы

Если JOIN содержит вложенные `joins[]` (nested joins), анализ применяется рекурсивно:
- Вложенные JOIN'ы обрабатываются тем же алгоритмом
- Родительский JOIN считается используемым, если хотя бы один из его вложенных JOIN'ов используется

### 3.5 Что исключается из FFL

При удалении неиспользуемого LEFT JOIN из FFL-ноды:
- Удаляется элемент из `from[].joins[]`
- Удаляется соответствующий элемент из `join_fields[]`
- Все остальные поля ноды (`select`, `where`, `group_by`, `having`) остаются без изменений

### 3.6 Порядок применения фильтрации

Фильтрация JOIN'ов выполняется **внутри `createNode()`** до того, как `buildLineage()` собирает `fullChildFields` для рекурсивного обхода. В результате:
- `condition_fields` удалённых LEFT JOIN'ов не попадают в `fullChildFields`
- Child-ноды, на которые ссылались только удалённые JOIN'ы, **не добавляются в `resultMap` для данного target-поля**
- Глобальное удаление нод из `nodeById` или из FULL_PARS **не производится** — ноды могут использоваться другими target-полями или ветками FFL

### 3.7 Каскадный эффект на downstream

Если LEFT JOIN удалён, и он был единственным источником ссылки на child-ноду (через `condition_fields[].child_fields[].nodeId`), то эта child-нода **не будет включена в FFL для данного target-поля**. Это происходит автоматически, т.к. `buildLineage()` собирает `fullChildFields` уже из отфильтрованной ноды, и рекурсивный вызов выполняется только для тех `nodeId`, которые остались в `select` / `where` / `group_by` / `having` / `join_fields` после фильтрации.

## 4. Входные данные

- `FULL_PARS/FULL_PARS_model_<basename>.json` — полная структура (источник для FFL)
- `full_field_lineage/<baseName>/.../FFL_*.json` — урезанная структура, в которой выполняется оптимизация

## 5. Выходные данные

- `full_field_lineage/<baseName>/.../FFL_*.json` — оптимизированная урезанная структура с исключёнными неиспользуемыми LEFT JOIN'ами

## 6. Граничные случаи

### 6.1 Все LEFT JOIN'ы используются
Если все LEFT JOIN'ы узла участвуют в полях/условиях — FFL не изменяется.

### 6.2 Нет LEFT JOIN'ов
Если в узле только INNER JOIN'ы — оптимизация не применяется.

### 6.3 LEFT JOIN используется только в условии другого LEFT JOIN
Если JOIN A (left) ссылается на JOIN B (left) в своём условии, и JOIN B используется — оба остаются.

### 6.4 Виртуальные таблицы в JOIN
Виртуальные таблицы (с `virtualTable`) обрабатываются как обычные JOIN'ы: если их поля не используются и тип `left` — исключаются.

## 7. Зависимости

- SRS01 full_pars — формат FULL_PARS и FFL
- SRS02 query_reconstruction — восстановленный SQL становится компактнее

## 8. Пример

**Вход (фрагмент FFL, узел 296):**
```json
{
  "from": [{
    "table": "ВТ_ПенсионныеСчета_Свойства",
    "alias": "ВТ_ПенсионныеСчета_Свойства",
    "joins": [
      {"joinType": "inner", "source": {"table": "ВТ_НеТранзитныеВидыНачалоКонец", "alias": "..."}, "condition": "..."},
      {"joinType": "left", "source": {"table": "ВТ_Суммы", "alias": "ВТ_Суммы"}, "condition": "..."},
      {"joinType": "left", "source": {"table": "ВТ_СхемыПенсионныхСчетов", "alias": "..."}, "condition": "..."},
      {"joinType": "left", "source": {"table": "ВТ_ФизическиеЛица", "alias": "..."}, "condition": "..."}
    ]
  }]
}
```

**Выход (после оптимизации для поля Взносы26):**
```json
{
  "from": [{
    "table": "ВТ_ПенсионныеСчета_Свойства",
    "alias": "ВТ_ПенсионныеСчета_Свойства",
    "joins": [
      {"joinType": "inner", "source": {"table": "ВТ_НеТранзитныеВидыНачалоКонец", "alias": "..."}, "condition": "..."},
      {"joinType": "left", "source": {"table": "ВТ_Суммы", "alias": "ВТ_Суммы"}, "condition": "..."}
    ]
  }]
}
```

`ВТ_СхемыПенсионныхСчетов` и `ВТ_ФизическиеЛица` удалены, т.к. их поля не используются в SELECT/WHERE/GROUP BY/HAVING поля `Взносы26`.
