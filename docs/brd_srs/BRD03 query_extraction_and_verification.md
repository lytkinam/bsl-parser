# BRD03: Извлечение запроса из FULL_PARS и сверка с первичным

## 1. Цель

На основании полной структуры `FULL_PARS` извлечь работающий SQL-запрос для каждого узла и сверить его с первичным (исходным) SQL-запросом из пакета. Извлечённый запрос должен **полностью совпадать** с первичным по семантике и структуре.

## 2. Входные данные

- `FULL_PARS/FULL_PARS_model_<basename>.json` — полная структура full_pars (все узлы, все поля, все условия)
- `SDBL_PARS/sdbl_parse_nodes_<basename>.json` — первичные тексты запросов (full text, comments, whitespace)
- `SDBL_PARS/query_texts_<basename>/node_N.sql` — альтернативный источник первичного текста

### 2.1 Что содержит FULL_PARS (релевантно для извлечения)

| Поле | Тип | Назначение |
|------|-----|------------|
| `id`, `name`, `type` | мета | Идентификация узла |
| `select[]` | массив | Поля SELECT с `alias`, `text`, `field_id` |
| `from[]` | массив | Источники данных (`table`, `virtualTable`, `subquery`, `alias`, `joins[]`) |
| `where` | строка | Условие WHERE (исходный текст) |
| `group_by[]` | массив строк | Поля GROUP BY (исходный текст) |
| `having` | строка | Условие HAVING (исходный текст) |
| `into` | строка | Имя ВТ для `ПОМЕСТИТЬ` |
| `order_by[]` | массив строк | Сортировка |
| `limitations` | строка | `ПЕРВЫЕ N`, `РАЗЛИЧНЫЕ` и т.д. |
| `union_nodes_ids` | массив | ID частей UNION (для виртуальных родителей) |
| `union_group_id` | число | ID виртуального родителя |
| `union_type` | строка | `union_all` или `union` |
| `subquery_ids` | массив | ID подзапросов |
| `upquery_id` | число | ID родительского узла |

### 2.2 Что НЕ используется для извлечения

- `*_fields` (`where_fields`, `group_by_fields`, `having_fields`, `condition_fields`) — используются только для построения `child_fields` внутри full_pars, для извлечения SQL не нужны
- `child_fields` — используются только для определения зависимостей между узлами

## 3. Выходные данные

### 3.1 Извлечённые запросы
- `EXTRACTED_QUERIES/<baseName>/<nodeId>_<nodeName>.sql` — текстовый файл с извлечённым SQL-запросом для каждого узла

### 3.2 Результат сверки
- `VERIFICATION/<baseName>/verification_report.json` — JSON-файл с результатами сверки:
  ```json
  {
    "baseName": "example_2",
    "totalNodes": 6,
    "matched": 5,
    "mismatched": 1,
    "nodes": [
      {
        "id": 0,
        "name": "ЗЛО",
        "status": "matched",
        "primaryHash": "sha256...",
        "extractedHash": "sha256..."
      },
      {
        "id": 4,
        "name": "Результат_2",
        "status": "mismatched",
        "differences": [
          "SELECT field order differs",
          "WHERE condition missing"
        ]
      }
    ]
  }
  ```

## 4. Основные требования

### 4.1 FULL_PARS — единственный источник для извлечения
Извлечение выполняется **исключительно по данным FULL_PARS**. Если какого-то поля не хватает в FULL_PARS для построения запроса — это требование к расширению FULL_PARS.

### 4.2 Использование первичных полей
Для построения SQL используются **первичные** текстовые поля:
- `where` — строка, используется как есть
- `group_by[]` — массив строк, перечисляется через запятую
- `having` — строка, используется как есть
- `from[].joins[]` — полная структура JOIN (тип, источник, условие)
- `into` — строка для `ПОМЕСТИТЬ`
- `order_by[]` — массив строк
- `limitations` — строка (`РАЗЛИЧНЫЕ`, `ПЕРВЫЕ N`)

### 4.3 UNION-родители

UNION-родитель — узел с непустым `union_nodes_ids`. Поведение зависит от `type`:

- **`temp_query` с `union_nodes_ids`** — генерирует самостоятельный SQL-запрос: `ВЫБРАТЬ ... ПОМЕСТИТЬ <into>` + UNION-части
- **`sub_query` с `union_nodes_ids`** — inline UNION-конструкция в скобках внутри родительского запроса; `ПОМЕСТИТЬ` не добавляется

UNION-части извлекаются как отдельные `ВЫБРАТЬ ...` и соединяются через `ОБЪЕДИНИТЬ ВСЕ` / `ОБЪЕДИНИТЬ`.

Если `union_type = "union_all"` — разделитель `ОБЪЕДИНИТЬ ВСЕ`, иначе `ОБЪЕДИНИТЬ`.

**Как это выглядит для `temp_query`:**
```sql
ВЫБРАТЬ
    ...
ПОМЕСТИТЬ ВТ_ИмяВТ            -- into вставляется в UNION_0
ИЗ
    ...

ОБЪЕДИНИТЬ ВСЕ

ВЫБРАТЬ
    ...
ИЗ
    ...
```

**Как это выглядит для `sub_query` (inline):**
```sql
ИЗ
    (
        ВЫБРАТЬ
            ...

        ОБЪЕДИНИТЬ ВСЕ

        ВЫБРАТЬ
            ...
    ) КАК ПодЗапрос
```

### 4.4 Обработка подзапросов

`from[].subquery` содержит **имя sub_query-ноды** из FULL_PARS (например, `Результат_2_SUB_1`). При извлечении SQL subquery-нода **не создаётся как отдельная ВТ** и не выводится top-level. Вместо этого её SQL вставляется **inline в скобках** внутри родительского запроса:

```sql
ИЗ
    (
        ВЫБРАТЬ
            ...
        ИЗ
            ...
    ) КАК ПодЗапрос
```

**Правила:**
- `sub_query`-ноды не имеют `ПОМЕСТИТЬ` и не заканчиваются `;`
- Поиск subquery-ноды выполняется по `subquery_ids` родителя: среди ID из `subquery_ids` выбирается нода, `name` которой совпадает с `from[].subquery`
- Если `sub_query`-нода имеет `union_nodes_ids` — inline-ится UNION-конструкция в скобках
- Зависимости `sub_query`-ноды (из её `child_fields[].node_id`) должны быть созданы **до** родительского запроса; они участвуют в топологической сортировке, но сами как отдельные запросы не выводятся
- Alias `ПодЗапрос` берётся из `from[].alias`; поля в `select[]` родителя ссылаются на него как `ПодЗапрос.Поле`

### 4.5 Виртуальные таблицы
`virtual_table` содержит конкретный текст со всеми параметрами (например, `РегистрНакопления.уп_Резервы.Остатки(&Дата, ...)`). Используется как есть.

### 4.6 Физические таблицы
Узлы, представляющие физические таблицы (leaf, `node_id=null` в `child_fields`), не создаются как отдельные запросы. Они используются в `FROM` / `JOIN` родительских запросов.

### 4.7 Условия
- Если `where` пуст/null — блок WHERE отсутствует
- Если `group_by[]` пуст — блок GROUP BY отсутствует
- Если `having` пуст/null — блок HAVING отсутствует
- JOIN восстанавливаются из `from[].joins[]`

### 4.8 Порядок запросов
Запросы в пакете идут в порядке топологической сортировки: сначала создаются ВТ-зависимости (листья графа), затем промежуточные узлы, в конце — target-нода. **Sub_query-ноды не генерируют отдельный SQL**, но их зависимости учитываются при сортировке родительских запросов.

### 4.9 Сверка с первичным запросом

Для каждого узла выполняется сверка извлечённого SQL с первичным:

1. **Нормализация** — оба текста приводятся к каноническому виде:
   - Удаление лишних пробелов и переносов строк
   - Приведение к верхнему регистру ключевых слов
   - Удаление комментариев
   - Нормализация алиасов (если `КАК` отсутствует — добавляется)

2. **Сравнение** — нормализованные тексты сравниваются посимвольно

3. **Результат**:
   - `matched` — тексты совпадают
   - `mismatched` — тексты различаются, с указанием различий

### 4.10 Отличие от BRD02 (query_reconstruction)

| Аспект | BRD02 (query_reconstruction) | BRD03 (query_extraction) |
|--------|------------------------------|--------------------------|
| Источник | FFL (урезанная структура) | FULL_PARS (полная структура) |
| Поля SELECT | Только поля, влияющие на target | Все поля узла |
| WHERE / GROUP BY / HAVING | Только условия, влияющие на target | Все условия узла |
| Цель | Восстановить урезанный запрос для отладки | Извлечь полный запрос и сверить с первичным |
| Выход | RESTORED_QUERIES/ | EXTRACTED_QUERIES/ + VERIFICATION/ |

## 6. Ограничения

- Извлечённый запрос содержит **все** поля и условия из FULL_PARS (в отличие от BRD02, где запрос урезан)
- Параметры запроса (`&Дата`, `&Организация`) сохраняются из оригинального текста
- `DROP`-запросы не включаются
- Сверка выполняется на уровне нормализованного текста, а не побайтового сравнения (форматирование может отличаться)

## 7. Зависимости

- SRS01 full_pars — формат FULL_PARS
- BRD02 query_reconstruction — алгоритм построения SQL (переиспользуется SqlGenerator)
