# SRS02: Восстановление урезанного запроса для выполнения в 1С

## 1. Введение

### 1.1 Цель

Определить требования к подсистеме восстановления SQL-запросов 1С (SDBL) на основании урезанной структуры `full_field_lineage` (FFL). Подсистема генерирует работающий пакет запросов, который можно выполнить в консоли запросов 1С или встроить в код конфигурации.

### 1.2 Область применения

Модуль SDQL, пакет `sdql/query_reconstruction/`. Разработка в ветке `develop`, коммиты содержат `Refs Redmine #646`.

### 1.3 Термины

| Термин | Описание |
|--------|----------|
| **FFL** | `full_field_lineage` — плоский массив узлов, урезанный под конкретное поле |
| **FULL_PARS** | Полная модель full_pars со всеми метаданными (from, into, order_by, unions) |
| **Query Reconstructor** | Компонент, преобразующий FFL + FULL_PARS в текст SDBL |
| **Restored Query** | Восстановленный SQL-файл, готовый к выполнению |

### 1.4 Ссылки

- `docs/brd_srs/BRD02 query_reconstruction.md`
- `docs/brd_srs/SRS01 full_pars.md`

## 2. Общее описание

### 2.1 Контекст

На входе подсистемы — результат работы `full_field_lineage`: плоский массив узлов, содержащий только поля, влияющие на target-поле. Для восстановления работающего запроса необходимо:
1. Получить недостающие метаданные из `FULL_PARS_model` (структура FROM, INTO, UNION, ORDER BY)
2. Построить SQL-текст для каждого узла
3. Упорядочить запросы топологически (сначала ВТ-зависимости)
4. Сформировать пакет запросов, разделённых `;`

### 2.2 Пользователи

Разработчики 1С, аналитики запросов. Используют восстановленный запрос для отладки, тестирования или извлечения подмножества данных.

### 2.3 Ограничения

- **Формат первичен** — пример middle_example определяет структуру выходного SQL
- **Пример первее кода** — `middle_example` генерируется до коммита кода
- **Поле `text`** — используется как основа для восстановления выражений
- **Минимальные изменения** — не изменять существующие модули full_pars

## 3. Функциональные требования

### 3.1 Входные данные

#### FR-3.1.1 FFL-файл
Путь: `full_field_lineage/<baseName>/<nodeId>_<nodeName>/FFL_<baseName>_<nodeId>_<nodeName>_<alias>.json`

#### FR-3.1.2 FULL_PARS_model
Путь: `FULL_PARS/FULL_PARS_model_<baseName>.json`

Используется для получения:
- `from[]` — структура источников данных (таблицы, алиасы, JOIN)
- `into` — имя ВТ для `ПОМЕСТИТЬ`
- `order_by` — сортировка
- `unions` — части UNION (для виртуальных родителей)
- `limitations` — ограничения (`ПЕРВЫЕ N`)
- `autoorder` — автоупорядочивание

### 3.2 Выходные данные

#### FR-3.2.1 Структура каталогов
```
RESTORED_QUERIES/
└── <baseName>/
    └── <nodeId>_<nodeName>/
        └── <alias>.sql
```

#### FR-3.2.2 Формат SQL-файла
Один текстовый файл с пакетом запросов SDBL, разделённых символом `;`. Кодировка UTF-8.

### 3.3 Построение запроса для узла

#### FR-3.3.1 SELECT
Для каждого поля `select[]`:
- Если `text == alias` или `text` равен одному слову без точки — выводим `text КАК alias`
- Если `text` содержит точку или выражение — выводим `text КАК alias`
- Исключение: `text = "0"`, `text = "ЛОЖЬ"`, `text = "ИСТИНА"`, `text = "NULL"` — выводим как есть с `КАК alias`

Поля перечисляются через запятую с переносом строки.

#### FR-3.3.2 INTO
Если `into != null` и `type == "temp_query"` — добавлять строку `ПОМЕСТИТЬ <into>` перед `FROM`.

#### FR-3.3.3 FROM
Восстанавливается из `FULL_PARS_model.from[]` для данного `node_id`:
- `table` — `ИЗ <table> КАК <alias>`
- `virtualTable` — `ИЗ <virtualTable> КАК <alias>`
- `subquery` (String) — `ИЗ <subquery> КАК <alias>` (имя ВТ, уже созданной ранее)
- `externalDataSource` — `ИЗ <externalDataSource> КАК <alias>`

Если `from[]` содержит несколько источников — они перечисляются через запятую (кросс-соединение).

#### FR-3.3.4 JOIN
Восстанавливается из `join_conditions[]` (из FFL) + метаданные из `FULL_PARS_model`:
- Тип: `ЛЕВОЕ СОЕДИНЕНИЕ`, `ПРАВОЕ СОЕДИНЕНИЕ`, `ПОЛНОЕ СОЕДИНЕНИЕ`, `ВНУТРЕННЕЕ СОЕДИНЕНИЕ`
- Источник: таблица / виртуальная таблица / ВТ
- Условие: `ПО <condition>`

#### FR-3.3.5 WHERE
Из `where_fields[].text`:
- Каждое поле — отдельное условие
- Соединяются через `И`
- Блок: `ГДЕ <condition1> И <condition2> И ...`

#### FR-3.3.6 GROUP BY
Из `group_by_fields[].text`:
- Блок: `СГРУППИРОВАТЬ ПО <field1>, <field2>, ...`

#### FR-3.3.7 HAVING
Из `having_fields[].text`:
- Блок: `ИМЕЮЩИЕ <condition>`

#### FR-3.3.8 ORDER BY
Из `FULL_PARS_model.order_by[]` (если присутствует):
- Блок: `УПОРЯДОЧИТЬ ПО <field1>, <field2>, ...`

#### FR-3.3.9 LIMITATIONS
Из `FULL_PARS_model.limitations`:
- Блок: `ПЕРВЫЕ <N>` (добавляется после `ВЫБРАТЬ`)

### 3.4 Обработка UNION

#### FR-3.4.1 Виртуальный родитель
Если узел имеет `union_nodes_ids` (виртуальный UNION-родитель):
1. Для каждой части UNION получить запрос из `FULL_PARS_model` по `union_id`
2. Соединить через `ОБЪЕДИНИТЬ ВСЕ` (если `union_type = "union_all"`) или `ОБЪЕДИНИТЬ` (если `union_type = "union"`)
3. Внешний `ПОМЕСТИТЬ` берётся из виртуального родителя (`into`)

#### FR-3.4.2 SELECT для UNION-частей
Каждая часть UNION содержит полный набор полей из `select[]` согласно FFL. Если FFL содержит только подмножество полей — только они включаются в SELECT каждой части.

### 3.5 Топологическая сортировка

#### FR-3.5.1 Алгоритм
1. Построить граф зависимостей из `child_fields[].node_id` (исключая `null`)
2. Выполнить топологическую сортировку (Kahn или DFS)
3. Узлы без зависимостей (только физические таблицы) — не создают отдельных запросов
4. Порядок вывода: от листьев к корню (сначала ВТ-зависимости, потом target)

### 3.6 Исключения

#### FR-3.6.1 Физические таблицы
Узлы, которые являются leaf (все `child_fields` имеют `node_id=null`), не порождают отдельных запросов. Они используются только в `FROM` / `JOIN` родительских запросов.

#### FR-3.6.2 DROP-запросы
`drop_query` не включаются в восстановленный пакет.

## 4. Структуры данных

### 4.1 RestoredQueryNode

Внутренняя структура для построения SQL:

```java
class RestoredQueryNode {
    int id;
    String name;
    String type;
    String into;
    List<String> selectExpressions;  // "СУММА(ПодЗапрос.ЗадолженностьПенсии) КАК ЗадолженностьПенсии"
    List<DataSource> from;           // из FULL_PARS_model
    List<RestoredJoin> joins;        // из join_conditions + FULL_PARS
    List<String> whereConditions;    // из where_fields[].text
    List<String> groupByFields;      // из group_by_fields[].text
    List<String> havingConditions;   // из having_fields[].text
    List<String> orderByFields;      // из FULL_PARS_model
    String limitations;              // из FULL_PARS_model
    List<RestoredQueryNode> unionParts; // для виртуальных родителей
}
```

### 4.2 RestoredJoin

```java
class RestoredJoin {
    String joinType;    // left, right, full, inner
    String sourceTable; // имя таблицы / ВТ
    String alias;       // алиас
    String condition;   // текст условия
}
```

## 5. Алгоритмы

### 5.1 Общий пайплайн

```
1. Прочитать FFL → List<FullFieldLineageNode>
2. Прочитать FULL_PARS_model → Map<nodeId, FullParsNode>
3. Построить граф зависимостей из child_fields[].node_id
4. Топологическая сортировка → List<nodeId> (от листьев к корню)
5. Для каждого nodeId:
   a. Получить FullParsNode из FFL
   b. Получить метаданные из FULL_PARS_model (from, into, order_by, unions)
   c. Построить RestoredQueryNode
   d. Сгенерировать SQL-текст
6. Объединить тексты через ";\n\n"
7. Записать в <alias>.sql
```

### 5.2 Построение SELECT

```
select_lines = []
for field in node.select:
    if field.text.equals(field.alias) or isLiteral(field.text):
        line = field.text + " КАК " + field.alias
    else:
        line = field.text + " КАК " + field.alias
    select_lines.add(line)

select_block = "ВЫБРАТЬ\n    " + join(select_lines, ",\n    ")
```

### 5.3 Построение UNION

```
if node.union_nodes_ids is not empty:
    union_queries = []
    for union_id in node.union_nodes_ids:
        union_node = full_pars[union_id]
        union_sql = buildQuery(union_node)
        union_queries.add(union_sql)
    
    separator = "\n\nОБЪЕДИНИТЬ ВСЕ\n\n"  // или "ОБЪЕДИНИТЬ"
    query = join(union_queries, separator)
    
    if node.into != null:
        query = query + "\n\nПОМЕСТИТЬ " + node.into
```

### 5.4 Топологическая сортировка

```
graph = buildGraph(ffl_nodes)
in_degree = calculateInDegrees(graph)
queue = nodes with in_degree == 0 (excluding physical-only leaves)
result = []

while queue not empty:
    node = queue.poll()
    result.add(node)
    for dependent in graph.dependents(node):
        in_degree[dependent]--
        if in_degree[dependent] == 0:
            queue.add(dependent)

return reverse(result)  // from leaves to root
```

## 8. Нефункциональные требования

### 8.1 Формат первичен
Выходной SQL определяется примером (раздел 7). Новые конструкции добавляются только по согласованию.

### 8.2 Пример первее кода
`middle_example` генерируется до коммита кода. Артефакты коммитятся отдельно от кода.

### 8.3 Читаемость
Восстановленный SQL должен быть отформатирован с отступами (как в оригинальных `query_texts_*.sql`).

## 9. Тестирование

### 9.1 Тест наличия файла
`testRestoredQueryFile()` — проверяет наличие `RESTORED_QUERIES/middle_example/74_ВТ_Суммы_ПР_ТранзитныеВиды/ЗадолженностьПенсии.sql`.

### 9.2 Тест синтаксиса
Проверяет, что восстановленный SQL содержит корректные блоки: `ВЫБРАТЬ`, `ИЗ`, `ПОМЕСТИТЬ` (для ВТ), `СГРУППИРОВАТЬ ПО`.

### 9.3 Тест порядка
