# BRD02: Восстановление урезанного запроса для выполнения в 1С

## 1. Цель

На основании урезанной структуры `full_field_lineage` (FFL) восстановить работающий пакет SQL-запросов 1С (SDBL), который можно выполнить в консоли запросов или в коде 1С:Предприятие.

## 2. Входные данные

- `FFL_<baseName>_<nodeId>_<nodeName>_<alias>.json` — урезанная структура full_pars (плоский массив узлов). **FFL самодостаточен**, содержит все необходимые поля для построения запроса.

### 2.1 Что содержит FFL (релевантно для восстановления)

| Поле | Тип | Назначение |
|------|-----|------------|
| `id`, `name`, `type` | мета | Идентификация узла |
| `select[]` | массив | Поля SELECT с `alias`, `text`, `field_id` |
| `from[]` | массив | Источники данных (`table`, `virtualTable`, `subquery`, `alias`, `joins[]`) |
| `where` | строка | Условие WHERE (исходный текст) |
| `group_by[]` | массив строк | Поля GROUP BY (исходный текст) |
| `having` | строка | Условие HAVING (исходный текст) |
| `into` | строка | Имя ВТ для `ПОМЕСТИТЬ` |
| `order_by[]` | массив строк | Сортировка |
| `limitations` | строка | `ПЕРВЫЕ N`, `РАЗЛИЧНЫЕ` и т.д. |
| `union_nodes_ids` | массив | ID частей UNION (для виртуальных родителей) |
| `union_group_id` | число | ID виртуального родителя |
| `union_type` | строка | `union_all` или `union` |
| `subquery_ids` | массив | ID подзапросов |

### 2.2 Что НЕ используется для восстановления

- `*_fields` (`where_fields`, `group_by_fields`, `having_fields`, `condition_fields`) — используются только для построения `child_fields` внутри full_pars, для восстановления SQL не нужны
- `child_fields` — используются только для определения зависимостей между узлами (порядок запросов)

## 3. Выходные данные

- `RESTORED_QUERIES/<baseName>/<nodeId>_<nodeName>/<alias>.sql` — текстовый файл с пакетом запросов SDBL, разделённых `;`

## 4. Режимы запуска

Подсистема поддерживает 4 режима запуска (CLI-параметры):

### 4.1 Конкретное поле
Вход: `{nodeId, alias}` (одно поле).  
Если FFL-файл для данного поля **отсутствует** — он создаётся автоматически через `FullFieldLineageBuilder`. Затем выполняется восстановление SQL.

### 4.2 Конкретная таблица (нода)
Вход: `nodeId` или `nodeName`.  
Для каждого поля `select[]` данной ноды создаётся/читается FFL и восстанавливается SQL. Результат — набор SQL-файлов (по одному на поле).

### 4.3 Общий запрос (пакет)
Вход: `baseName` (без указания конкретной ноды).  
Определяются target-ноды:
1. Все `result` узлы
2. Если нет — последний `temp_query`
3. Если нет — последний UNION-родитель (`temp_query` с `union_nodes_ids`)

Для каждой target-ноды и каждого её поля `select` — создаётся/читается FFL и восстанавливается SQL.

### 4.4 Пересоздание зависимых таблиц
Отдельный флаг `--recreate-deps`.  
При восстановлении SQL в пакет добавляются команды `УНИЧТОЖИТЬ` для всех ВТ перед их созданием (`ПОМЕСТИТЬ`). Это последний шаг, который может выполняться после изменения первичного запроса.  
Порядок: изменение SQL → перегенерация SDBL_PARS/LINE_PARS/FULL_PARS/FFL → восстановление SQL с `--recreate-deps`.

## 5. Основные требования

### 5.1 FFL — единственный источник
Восстановление выполняется **исключительно по данным FFL**. Если какого-то поля не хватает в FFL для построения запроса — это требование к расширению FFL, а не к обращению к `FULL_PARS_model`.

### 5.2 Использование первичных полей
Для построения SQL используются **первичные** текстовые поля:
- `where` — строка, используется как есть
- `group_by[]` — массив строк, перечисляется через запятую
- `having` — строка, используется как есть
- `from[].joins[]` — полная структура JOIN (тип, источник, условие)
- `into` — строка для `ПОМЕСТИТЬ`
- `order_by[]` — массив строк
- `limitations` — строка (`РАЗЛИЧНЫЕ`, `ПЕРВЫЕ N`)

### 5.3 UNION-родители

UNION-родитель — узел с непустым `union_nodes_ids`. Поведение зависит от `type`:

- **`temp_query` с `union_nodes_ids`** — генерирует самостоятельный SQL-запрос: `ВЫБРАТЬ ... ПОМЕСТИТЬ <into>` + UNION-части
- **`sub_query` с `union_nodes_ids`** — inline UNION-конструкция в скобках внутри родительского запроса; `ПОМЕСТИТЬ` не добавляется

UNION-части восстанавливаются как отдельные `ВЫБРАТЬ ...` и соединяются через `ОБЪЕДИНИТЬ ВСЕ` / `ОБЪЕДИНИТЬ`.

Если `union_type = "union_all"` — разделитель `ОБЪЕДИНИТЬ ВСЕ`, иначе `ОБЪЕДИНИТЬ`.

**Как это выглядит для `temp_query`:**
```sql
ВЫБРАТЬ
    ...
ПОМЕСТИТЬ ВТ_ИмяВТ            -- into вставляется в UNION_0
ИЗ
    ...

ОБЪЕДИНИТЬ ВСЕ

ВЫБРАТЬ
    ...
ИЗ
    ...
```

**Как это выглядит для `sub_query` (inline):**
```sql
ИЗ
    (
        ВЫБРАТЬ
            ...

        ОБЪЕДИНИТЬ ВСЕ

        ВЫБРАТЬ
            ...
    ) КАК ПодЗапрос
```

### 5.4 Обработка подзапросов

`from[].subquery` содержит **имя sub_query-ноды** из FFL (например, `ВТ_Суммы_ПР_ТранзитныеВиды_SUB_1`). При восстановлении SQL subquery-нода **не создаётся как отдельная ВТ** и не выводится top-level. Вместо этого её SQL вставляется **inline в скобках** внутри родительского запроса:

```sql
ИЗ
    (
        ВЫБРАТЬ
            ...
        ИЗ
            ...
    ) КАК ПодЗапрос
```

**Правила:**
- `sub_query`-ноды не имеют `ПОМЕСТИТЬ` и не заканчиваются `;`
- Поиск subquery-ноды выполняется по `subquery_ids` родителя: среди ID из `subquery_ids` выбирается нода, `name` которой совпадает с `from[].subquery`
- Если `sub_query`-нода имеет `union_nodes_ids` — inline-ится UNION-конструкция в скобках
- Зависимости `sub_query`-ноды (из её `child_fields[].node_id`) должны быть созданы **до** родительского запроса; они участвуют в топологической сортировке, но сами как отдельные запросы не выводятся
- Alias `ПодЗапрос` берётся из `from[].alias`; поля в `select[]` родителя ссылаются на него как `ПодЗапрос.Поле`

### 5.5 Виртуальные таблицы
`virtual_table` содержит конкретный текст со всеми параметрами (например, `РегистрНакопления.уп_Резервы.Остатки(&Дата, ...)`). Используется как есть.

### 5.6 Физические таблицы
Узлы, представляющие физические таблицы (leaf, `node_id=null` в `child_fields`), не создаются как отдельные запросы. Они используются в `FROM` / `JOIN` родительских запросов.

### 5.7 Условия
- Если `where` пуст/null — блок WHERE отсутствует
- Если `group_by[]` пуст — блок GROUP BY отсутствует
- Если `having` пуст/null — блок HAVING отсутствует
- JOIN восстанавливаются из `from[].joins[]`

### 5.8 Порядок запросов
Запросы в пакете идут в порядке топологической сортировки: сначала создаются ВТ-зависимости (листья графа), затем промежуточные узлы, в конце — target-нода. **Sub_query-ноды не генерируют отдельный SQL**, но их зависимости учитываются при сортировке родительских запросов.

### 5.9 Общая конструкция с inline-subquery

```sql
-- 1. Зависимая ВТ (используется внутри subquery)
ВЫБРАТЬ
    ...
ПОМЕСТИТЬ ВТ_Зависимость
ИЗ
    ...
;

-- 2. Родительский запрос с inline-subquery
ВЫБРАТЬ
    ПодЗапрос.Поле1 КАК Поле1,
    ПодЗапрос.Поле2 КАК Поле2
ПОМЕСТИТЬ ВТ_Родитель
ИЗ
    (
        ВЫБРАТЬ
            ...
        ИЗ
            ВТ_Зависимость КАК ВТ_Зависимость
    ) КАК ПодЗапрос
;
```

### 5.10 Общая конструкция UNION с inline-subquery

```sql
-- 1. Зависимые ВТ (используются внутри UNION-частей subquery)
ВЫБРАТЬ
    ...
ПОМЕСТИТЬ ВТ_Зависимость1
ИЗ
    ...
;

-- 2. Родительский запрос с inline UNION-subquery
ВЫБРАТЬ
    ПодЗапрос.Поле1 КАК Поле1
ПОМЕСТИТЬ ВТ_Родитель
ИЗ
    (
        ВЫБРАТЬ
            ...
        ИЗ
            ВТ_Зависимость1 КАК ВТ_Зависимость1

        ОБЪЕДИНИТЬ ВСЕ

        ВЫБРАТЬ
            ...
        ИЗ
            ...
    ) КАК ПодЗапрос
СГРУППИРОВАТЬ ПО
    ...
;
```

## 7. Ограничения

- Восстановленный запрос содержит только поля, присутствующие в FFL. Поля, не влияющие на результат target-поля, отсутствуют.
- Параметры запроса (`&Дата`, `&Организация`) сохраняются из оригинального текста.
- `DROP`-запросы не включаются (кроме режима `--recreate-deps`).
