# BRD10 — SDQL CLI: Интерфейс командной строки для SQL-анализатора 1С

**Версия:** 1.0  
**Дата:** 2026-06-06  
**Статус:** Черновик  
**Задача Redmine:** #646  
**Основание:** INTRO 10 CLI.MD — принципы интеграции классических сервисов через CLI

---

## 1. Обзор

SDQL CLI — это изолированный интерфейс командной строки для SQL-анализатора 1С (SDQL). Сервис предоставляет AI-агентам доступ к разбору SQL-запросов через стандартные потоки ввода/вывода (stdin/stdout), без прямых импортов функций или сетевых вызовов.

**Ключевой принцип:** MCP-сервер MCP_QUERY_1C (порт 15372) взаимодействует с SDQL-парсером не по HTTP (порт 5372), а через CLI-вызовы. Это делает парсер заменяемым «чёрным ящиком».

---

## 2. Заинтересованные стороны

| Роль | Описание |
|------|----------|
| AI-агент / Kimi CLI | Потребитель CLI — вызывает команды через stdin, получает JSON через stdout |
| MCP_QUERY_1C (BRD08) | Основной клиент CLI — оборачивает вызовы в MCP-методы |
| Аналитик НПФ | Конечный пользователь результатов анализа |
| Разработчик SDQL | Может переписывать внутреннюю архитектуру парсера без изменения CLI-контракта |

## 3. Бизнес-требования (REQ)

### REQ-10.01 Изоляция через stdin/stdout
CLI-инструмент должен принимать входные данные исключительно через аргументы командной строки и/или stdin. Результат возвращается через stdout. Не допускаются прямые импорты Java-классов или HTTP-вызовы внутри кодовой базы агента.

### REQ-10.02 Жёсткий контракт входных данных
Каждая команда CLI должна:
- Иметь чётко определённые обязательные и опциональные аргументы.
- Поддерживать флаг `--help` с описанием команды, аргументов и примеров использования.
- Проводить строгую валидацию входных данных до начала бизнес-логики.

### REQ-10.03 Таксономия кодов возврата
Сервис должен возвращать детерминированные exit-коды:

| Код | Значение | Действие агента |
|-----|----------|-----------------|
| 0 | Успех | Обработать результат |
| 1 | Сетевая ошибка (для команд, требующих внешних вызовов) | Повторить запрос или сообщить о недоступности |
| 2 | Ошибка валидации входного контракта | Исправить формат данных и повторить |
| 3 | Ошибка разбора SQL (синтаксис, семантика) | Проверить корректность SQL-запроса |
| 4 | Внутренняя ошибка | Обратиться к разработчику |

При коде 2 агент должен получить структурированное описание ошибки валидации (какое поле, какое ожидалось, что получено).

### REQ-10.04 Изоляция от глобального состояния
Поведение CLI не должно зависеть от скрытого глобального состояния. Все данные (SQL-текст, директория артефактов, режим детализации) передаются явно через аргументы.

### REQ-10.05 Заменяемость (Progressive Disclosure)
Внутренняя архитектура парсера (ANTLR4, Jackson, JGraphT) скрыта от потребителя CLI. Пока CLI-контракт стабилен, реализация может быть полностью переписана без влияния на потребителей.

### REQ-10.06 Поддержка команд анализа
CLI должен предоставлять команды, эквивалентные MCP-методам BRD06:

| Команда | Описание | Аналог MCP |
|---------|----------|-----------|
| `analyze` | Полный разбор SQL-пакета | `analyze_sql_package` |
| `sdbl-model` | Получить SDBL модель | `get_sdbl_model` |
| `line-pars-model` | Получить LINE_PARS модель | `get_line_pars_model` |
| `full-pars-model` | Получить FULL_PARS модель | `get_full_pars_model` |
| `hierarchy` | Получить иерархию узлов | `get_hierarchy` |
| `field-lineage` | Получить lineage поля | `get_field_lineage` |
| `full-field-lineage` | Получить полный lineage | `get_full_field_lineage` |
| `restore-query` | Восстановить SQL-запрос | `get_restored_query` |
| `list-nodes` | Список узлов | `list_nodes` |
| `verify` | Отчёт верификации | `get_verification_report` |

### REQ-10.07 Формат выходных данных
Результат каждой команды должен возвращаться в формате JSON. Структура JSON определяется контрактом команды и не зависит от внутренних классов Java.

### REQ-10.08 Работа с артефактами
Команды, требующие доступа к ранее созданным артефактам (`sdbl-model`, `hierarchy` и т.д.), должны принимать путь к директории артефактов через аргумент `--artifacts-dir`.

### REQ-10.09 Режим Online и Offline
Команда `analyze` должна поддерживать два режима:
- **Offline** (по умолчанию): SQL-текст передаётся через `--sql-file` или stdin, артефакты сохраняются в `--output-dir`.
- **Online**: Анализ выполняется во временной директории, артефакты не сохраняются (для одноразовых запросов).

## 4. Бизнес-объекты

### OBJ-10.001 CliRequest (Входной контракт)
```json
{
  "command": "analyze",
  "args": {
    "sqlText": "ВЫБРАТЬ 1 КАК Поле1 ПОМЕСТИТЬ ВТ_Тест",
    "outputDir": "/tmp/sdql-output",
    "baseName": "test_query",
    "detailed": false
  }
}
```

### OBJ-10.002 CliResponse (Выходной контракт при успехе)
```json
{
  "success": true,
  "exitCode": 0,
  "data": {
    "baseName": "test_query",
    "nodesCount": 1,
    "targetNodes": [...]
  }
}
```

### OBJ-10.003 CliError (Выходной контракт при ошибке)
```json
{
  "success": false,
  "exitCode": 2,
  "errorCode": "MISSING_INPUT",
  "message": "sqlText is required for command 'analyze'",
  "details": {
    "field": "sqlText",
    "expected": "non-empty string",
    "received": null
  }
}
```

## 5. Интеграции

### INT-10.001 MCP_QUERY_1C → SDQL CLI
- **Транспорт:** Process spawn (stdin/stdout)
- **Формат:** JSON в stdin → JSON из stdout
- **Exit-код:** 0–4 согласно REQ-10.03
- **Пример вызова:**
  ```bash
  echo '{"command":"analyze","args":{"sqlText":"...","outputDir":"..."}}' | \
    java -cp bsl-parser.jar com.github._1c_syntax.bsl.parser.sdql.cli.SdqlCli
  ```

### INT-10.002 SDQL Pipeline (BRD06)
- **Интерфейс:** `SdqlPipeline.analyze(sqlText, outputDir, baseName, detailed)`
- **CLI вызывает:** Pipeline напрямую (внутри JVM), не через HTTP

---

## 6. Ограничения и допущения

- CLI работает внутри JVM (Java 17+), запуск через `java -cp ...`.
- Для интеграции с MCP_QUERY_1C требуется, чтобы CLI и MCP-сервер работали в одной файловой системе (общий доступ к `--artifacts-dir`).
- CLI не предоставляет интерактивный REPL — только одноразовые команды.
- Параллельные вызовы CLI из разных процессов безопасны при условии использования разных `--output-dir`.
